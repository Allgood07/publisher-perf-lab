# Publisher: 5 минут на 800 чтениях/с и диагностика 1 200/с

**26 ноября 2026 UTC.** Локальный Publisher `ec1b5ce9fc45d7b2d33957957953f10a83c390a4`. Это продолжение [сравнения раздельных квот](publisher-k6-split-cpu.md), не нагрузка на Site.pro и не SLA. Цель — проверить длительное окно и локализовать пропуски, не увеличивая темп выше 1 200/с.

## Протокол

- `endurance`: один и тот же темп 800 чтений/с, 5 секунд разминки, 300 секунд измерения. Три повтора без автора и три с одним автором, то есть по 240 000 плановых чтений на прогон. С автором — 85 последовательных публикаций с плановым интервалом 3,5 секунды.
- `diagnostic`: 5 секунд разминки, 30 секунд при 1 200 чтениях/с, три повтора на профиль. С автором — восемь последовательных публикаций. Телеметрия включена только в диагностике: сериализация метрик, CSV и работа сборщика могут изменить сам прогон.
- Пороги прежние: все запланированные чтения с проверенным содержимым, без пропусков, HTTP-ошибок или несовпадений; p95 GET ≤ 20 мс и p99 ≤ 50 мс. С автором — все публикации наблюдаются как точная новая версия, p95 видимости ≤ 100 мс. Процентили не включают незапущенные запросы.
- Каждый запуск — свежие контейнеры. Publisher — 1 CPU, k6 — 2 CPU, по 384 MiB и 128 PID. Общий loopback с `--network none`, без наружных портов. Ubuntu/GitHub Actions здесь не участвует: CI выполняет только обычный smoke. Среда: MacBookPro18,3, macOS 15.7.4, Docker Desktop Engine 24.0.5 (`linux/arm64`, VM 4 vCPU, около 7,8 GiB), Node 22.22.0, k6 1.0.0.

```sh
git submodule update --init
node split-cpu.mjs endurance /tmp/publisher-endurance 3 800
node split-cpu.mjs diagnostic /tmp/publisher-diagnostic 3 1200
node collect-final-series.mjs /tmp/publisher-endurance /tmp/publisher-diagnostic /tmp/publisher-final.json
```

Каталоги должны быть новыми. Серии идут последовательно, профили чередуются: чтение первым в повторах 1 и 3, публикация первой в повторе 2. Для каждого запуска сохраняется ревизия обвязки, исходный gitlink, код выхода и измеренные метрики. Прерванный запуск — не штатный замер.

## Как читать посекундные данные

CSV метрик k6 агрегируется по секундам UTC в контейнере, сырой поток не хранится. Учитываются только завершённые чтения и пропуски сценария `reader`. Для каждой секунды сохраняются количество чтений и пропусков, среднее и максимум длительности GET, встроенные показания `vus` и максимум выборочного `exec.instance.vusActive` (каждая 64-я измеряемая итерация). Это наблюдаемый максимум, а не точный пик и не число HTTP-запросов в полёте. Сэмплы CPU — накопительные `usage_usec`, `nr_throttled`, `throttled_usec` каждого контейнера, примерно раз в секунду. Для приблизительного сравнения берём разность между соседними отсчётами: окно и метрики могут расходиться по границе секунды, поэтому совпадение не доказывает причину, а отсутствие совпадения не исключает короткий пик. Квоты — лимиты, не закреплённые ядра.

## Результаты

| Темп и окно | Профиль | Полных прогонов | Пропуски k6 по повторам | p95 GET, мс | p99 GET, мс |
| --- | --- | ---: | --- | ---: | ---: |
| 800/с, 300 с | Только чтение | 3/3 | 0 / 0 / 0 | 0,75–0,83 | 2,30–2,77 |
| 800/с, 300 с | С публикациями | 2/3 | 23 / 0 / 0 | 0,67–0,69 | 2,04–2,47 |
| 1 200/с, 30 с с телеметрией | Только чтение | 2/3 | 0 / 2 / 0 | 0,32–0,34 | 1,09–1,25 |
| 1 200/с, 30 с с телеметрией | С публикациями | 3/3 | 0 / 0 / 0 | 0,32–0,51 | 1,15–2,44 |

При 800/с завершилось **1 439 978 из 1 440 000** чтений. Один прогон с автором недобрал 22 чтения, хотя k6 зарегистрировал 23 пропуска. Это разные величины: планировщик может учитывать дополнительные вызовы у границы окна, а критерий требует именно запланированное число полных HTTP-наблюдений и ноль пропусков. Все **255 публикаций** увидели с первой пробы, максимум 2 мс после `303`. На 1 200/с завершилось **215 999 из 216 000** чтений; все 24 публикации видны с первой пробы, максимум 1 мс. HTTP-ошибок и несовпадений содержимого в обеих сериях не было. Худшие единичные GET — 98,41 мс на 800/с и 50,28 мс на 1 200/с с телеметрией, хотя p95 и p99 каждого прогона были ниже порогов.

### Что совпало с пропусками при 1 200/с

Во втором прогоне без автора оба пропуска случились в одной секундной корзине (`1795705886` UTC Unix). В ней k6 завершил 1 198 чтений; максимум GET — 50,28 мс против 3,76 и 4,91 мс в соседних корзинах. Выборочный максимум активных VU вырос до 39 против 2 и 3 рядом; предельные 96 по этим пробам не наблюдались. В приблизительно соответствующем интервале cgroup k6 зарегистрировал один период throttling, Publisher — ноль. При этом периоды throttling k6 были и на прогонах без пропусков. **Это совпадение, а не установленная причина.** Секундная выборка не видит всякий пик; сборщик CSV и семплеры сами добавляют работу, поэтому не сравниваем напрямую число пропусков с прежними прогонами без телеметрии.

[Машиночитаемые результаты и посекундные данные](publisher-k6-final.json). Серия 800/с снята на `5291878`, до добавления телеметрии; серия 1 200/с — на `c3a6cb9`. SHA и настройки записаны в данных. Статическое ревью отдельно проверило протокол и ограничения интерпретации; тесты и замеры выполнил исполнитель.

## Решение

**800/с держались пять минут во всех трёх прогонах без автора, но не во всех прогонах с публикациями.** При строгом требовании «ноль пропусков» не считаю этот темп подтверждённым для смешанного профиля. На 1 200/с снова встретился недобор при низких процентилях; есть наблюдение на стороне генератора, но потолок Publisher и причина пропусков не доказаны. На этом эксперимент закончен: не повышаем нагрузку и не оптимизируем сервис без подтверждённого узкого места.
